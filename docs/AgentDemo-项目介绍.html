CHAPTER 01

这个项目，究竟解决什么问题？

先用一句话描述产品，再解释它比一次模型调用多做了哪些工作。面试官首先想知道的是：谁会用它，能完成什么事，你解决了什么工程问题。

AgentDemo 是一个以 LangGraph 编排执行流程、以 PostgreSQL 保存状态、以 ToolExecutor 管住工具调用的个人 AI 助手应用。

用户可以连续对话、上传资料提问、读取网页或仓库内容，也可以提交后台任务和定时任务。系统负责带上相关历史与知识、选择合适的处理路径、在需要时征求工具授权、流式展示过程，最后保存答案与执行记录。

CONTEXT / 理解材料

带着资料回答

上传 TXT、Markdown 或可提取文字的 PDF。检索相关片段，保留来源和位置；长对话通过摘要保留必要背景。

ACTION / 使用能力

调用真实工具

通过本地插件或 MCP 读取文件、搜索网页和访问外部服务。需要授权的操作先暂停，确认后继续。

CONTINUITY / 持续工作

把工作交给后台

持久化任务进度和结果，支持一次性、间隔与每日调度，并处理并发抢占、取消和故障恢复。

使用场景系统实际完成的工作可检查的结果
“根据这份方案回答问题”文档解析 → 分块入库 → 混合检索 → 带证据生成Sources 中的文档、片段与检索方式
“总结这个网页 / 仓库 README”识别 URL → 选取 Fetch / GitHub MCP → 审批 → 执行 → 回答确认卡片、工具历史与来源
“今天有哪些 AI 新闻”识别时效意图 → web_search → 可选网页补充抓取搜索结果与后续 Fetch 的独立审批
“后台帮我整理这个主题”建立 Task → 数据库队列 → Worker 复用 AgentRuntime任务状态、进度、对话及工具审计
“以后每天执行这个任务”创建时区明确的 schedule → 到期生成 Task下次运行时间、派发决策和任务结果
“本地优先”的准确含义

会话、文档、任务和审计由本地应用与数据库管理；模型、Embedding、搜索、MCP 或可选重排仍可能访问外部服务。它不等于所有推理离线，也不等于数据永不出机。

项目的核心价值：把不稳定的模型与外部服务，放入有状态、有边界、有反馈、可验证的应用流程。能否恢复审批、阻止重复副作用、解释失败，比单纯展示一段回答更能体现工程能力。

CHAPTER 02

先看全局：五层，三条边界

阅读这张图时，沿着“界面 → API → 运行时”往下，再看运行时连接的知识、模型和工具。数据库保存事实，SSE 把过程反馈给用户。

层 / 技术负责什么选择理由与代价
展示层 · React / Vite聊天、事件解析、确认卡、来源和任务面板组件与交互生态成熟；流式状态和异步竞态需要专门处理。
接口层 · FastAPI / Pydantic参数校验、依赖注入、认证、路由、SSE便于异步 I/O 与类型化 API；CPU 密集操作仍需移出事件循环。
编排层 · LangGraph用状态和条件边连接检索、规划、工具、生成等节点流程和退出条件更显式；持久化与恢复语义仍由业务代码实现。
能力层 · Gateway / Executor / RAG隔离模型协议、工具策略与证据检索边界清楚、可注入 fake 测试；模块之间的契约需要维护。
存储层 · SQLAlchemy / PostgreSQL / pgvector关系数据、JSONB 运行元数据、向量及行锁事务和向量同库，部署简单；扩大数据量后需要评估索引与队列扩展。
三条边界，记住就能讲清架构

① API 决定“这个用户能读写什么”；② Runtime 决定“下一步做什么”；③ ToolExecutor 决定“这个工具调用能不能执行、如何记录”。不要让规划器直接绕过执行器调用工具。

CHAPTER 03

沿着一次提问，把系统走一遍

入口是 POST /api/conversations/chat/stream。请求正文带 message、可选 conversation_id 和任务类型；路由先检查登录身份和会话归属，再把事件流交给前端。

  1. 先确定“谁在问、在哪段对话里问”

    建立或读取所属会话，加载近期消息和有效摘要，必要时用第一条消息生成标题，再保存本轮用户输入。

  2. 为回答准备上下文，或尽早显示审批

    普通请求进入检索；明确的可审批网页 / GitHub 请求可以先触发确认，避免等待无关的知识检索。检索阶段还可能读取 MCP 的资源与提示模板。

  3. 规划工具，再把结果变成 observation

    Planner 输出工具名、参数、原因与确认要求；Executor 返回成功、失败或超时。运行时把有界结果整理为模型上下文。默认工具轮次上限为 3；固定路由通常在完成目标工具后结束。

  4. 生成、清洗、保存、收尾

    模型文本经过协议清洗再成为 token；最终保存正文、引用、工具轨迹和模型路由等元数据。摘要更新发生在答案提交之后，失败不会回滚已保存的答案。

CHAPTER 04

规划决定“做什么”，执行器决定“怎么做”

先分清两个职责：选工具是一项决策，运行工具是一项受控操作。工具结果只提供观察，不能自行提升权限。

用户意图当前路由关键行为
GitHub 仓库 / 文件链接GitHub MCP · get_file_contents解析 owner、repo、path、ref；识别 README 请求；缺少对应工具时明确说明。
明确要求读取本地文件本地 read_file 插件提取路径；按插件自己的允许路径规则读取 UTF-8 文本。
普通网页链接Fetch MCP · mcp.fetch.fetch读取网页内容；Fetch 的审批、URL 策略、超时均由统一链路约束。
Hugging Face 模型 / 数据集等Hugging Face MCP 专用路由识别资源类型并挑选可用服务工具，保留专门的参数构造。
时效、新闻、外部信息查询本地 web_search 插件可使用模型规范化搜索词；搜索供应商需配置；选中结果可再进入 Fetch 审批。
显式点名 MCP 工具ModelGateway.plan_tool_call 接口当前默认实现主要匹配工具名，返回结构化计划；并未执行一次通用 LLM 工具推理。
没有工具需求no_tool用已有历史、摘要与检索证据生成回答。
面试时准确描述规划能力

当前是规则驱动、带受限循环的 Agent 执行流程。虽然留有 plan_tool_call 抽象，但默认实现是工具名称匹配；不能把它讲成成熟的自主多步 ReAct 推理系统。后续可以在同一执行边界前接入真正的结构化 LLM 规划。

一个工具的“合同”是什么？

本地插件由 manifest.json 声明名称、参数 schema、权限标签、确认要求、超时、输出策略和入口函数。启动时扫描并注册；MCP 工具也会转成统一的注册结构。因此运行时不需要为每个供应商复制一套审计和授权逻辑。

正常返回也要处理

工具输出受到全局与工具自身长度策略约束。MCP 的结构化内容和文本被规范化；二进制媒体不会直接塞进模型文本。远端 isError 必须被解释为失败。

超时不等于撤回

取消等待可以阻止后续步骤，但已发出的 HTTP 请求或运行中的 Python 线程可能继续。必须保留“不确定结果”的审计，而不是自动再执行一次。

安全边界不是沙箱

Schema 校验解决“参数是否合法”，确认解决“用户是否授权”，MCP policy 解决“服务与工具是否允许”。本地 Python 插件仍在应用权限内执行，并没有完整的进程 / 容器隔离。

CHAPTER 05

为什么刷新页面后，仍然能继续确认？

因为待确认状态保存在数据库，而不是只存在 React 的内存里。确认请求认领的是服务器保存的计划，不是让浏览器临时提交一个任意工具调用。

把恢复过程拆成四个动作

  1. 保存快照

    建立一条正文为空的 assistant Message；它的 ID 就是 approval_id。JSONB metadata 保存 approval、tool_calls、citations 和 continuation。空审批消息不会进入正常模型历史。

  2. 原子认领

    确认接口拿数据库行锁，匹配用户、会话、工具名、参数、原消息和任务类型，再检查 pending / expiry。状态先变为 approved 并提交，重复、篡改、过期请求返回 409。

  3. 恢复已完成的观察

    确认模式重新加载历史，同时恢复先前引用、工具结果与搜索抓取队列；不会重做已经完成的搜索，也不会重复写入原用户消息。该模式执行获准工具后进入生成，或再次等待队列中的下一项审批。

  4. 记录最终状态

    成功结束标记 completed；用户取消保存 cancelled；中断保留 consumed / interrupted，不自动变回 pending。先查看工具历史，再决定是否发起新的工作。

这项设计牺牲了什么，换来了什么？

“先消费审批，再执行”会留下一个窗口：审批已被消费，进程却可能在真正调用工具之前崩溃。系统选择不自动重放，优先避免重复副作用。这不是跨外部系统的 exactly-once 承诺。

对照源码 · tool_approvals.py / conversations.py / runtime.py

CHAPTER 06

MCP 是能力连接层，权限仍由应用负责

可以把 MCP 理解为工具、资源和提示模板的标准化连接协议。它让 AgentDemo 接入多个外部能力服务，但“发现了一个工具”不等于“被允许运行这个工具”。

对象在项目中的用途需要分清的边界
Tools发现工具 schema → 注册 → 规划 → 执行工具调用不可绕过 ToolExecutor。
Resources读取文本作为上下文，或导入知识库资源读取有独立客户端路径；不要把它描述为工具执行，也不要隐式抓取资源链接。
Prompts加载服务器提供的提示模板作为补充它不是用户授权，也不能覆盖应用权限策略。
Discovery / Refresh有界并发、分页、缓存目录、原子替换远端工具缓存的是目录元数据，不是工具执行结果。
连接状态configured / ready / mock / errorready 是上次协商成功，不代表持续在线或持有长连接。

为什么 Fetch 单独一个环境？仓库中的 Fetch 服务和后端依赖不同代的 MCP SDK，因此在 mcp/fetch 使用独立 uv 项目与锁文件。协议连接跨越进程边界，Python 依赖不必强行装进同一个虚拟环境。

已经有的适配，与仍需做的产品化

代码包含本地 AgentDemoMcpServer 适配类，可把本地插件转成 MCP 风格接口；当前 FastAPI 入口主要挂载管理路由。不要仅凭这个类就声称已经发布了完整、独立可部署的 MCP 网络服务器。

CHAPTER 07

RAG：先找证据，再让模型组织答案

RAG（检索增强生成）解决的是“模型不知道你的资料”。模型权重没有因为上传文档而改变；应用只在回答时检索少量相关原文，并把它们放入本次上下文。

七个步骤，分别在解决什么问题？

步骤作用当前实现的准确边界
1 · 文档解析把资料转换成可检索文本支持 TXT / Markdown / 可提取文字的 PDF；没有 OCR 管线。PDF 偏移是提取后文本位置，不是原页面坐标。
2 · 分块与重叠控制证据长度，减少跨段信息丢失默认 chunk_size=900、overlap=120，单位为字符；会尽量沿段落边界切分。
3 · 上下文前缀让孤立片段带上主题抽取文档标题和 Markdown 章节层级；没有对每块调用模型生成 contextual summary。
4 · 两路召回语义找近义表达，词法找精确标识符pgvector 精确向量检索 + SQL 词法排序；词法不是 BM25，目前也没有 HNSW 索引。
5 · RRF 融合组合不同量纲的检索结果按名次累加倒数贡献；同分共享名次。融合分数是排序信号，不是答案正确概率。
6 · 可选重排 + MMR提高证据顺序，避免多条近乎重复内容默认本地 MMR；API 重排需显式启用兼容服务。MMR 基于顺序相关性与字符片段重合度。
7 · 引用持久化回答刷新后仍可查证保存原文、来源、片段位置、检索方法、重排 / 回退状态和上下文路径。
RRF(d) = Σ 1 / (60 + rankchannel(d))

只在两路都存在时做融合。例如 A 在两路都排第 1，得分约 0.0328；B 只在一路排第 1，约 0.0164。它表达“多路共同支持”，不表达 3.28% 的正确率。

检索失败时怎么办？

Embedding 不可用时，词法检索仍可工作；重排失败时回退到本地融合与 MMR；整体检索超时会报告状态，再使用已有上下文回答。系统不能把缺少证据包装成已查证事实。

已有文档怎么升级？

Reindex 更新检索上下文与向量，保留 chunk ID、原文和引用位置。重新生成 Embedding 失败时保留已有向量，避免一次网络故障毁掉可用索引。

知识权限在检索之前就过滤

检索范围是当前用户拥有的文档，再按当前会话及该用户的全局文档限定。这里“全局”指用户范围内没有绑定某个会话的文档，不是全体用户共享的资料。

CHAPTER 08

记忆负责延续对话，RAG 负责寻找资料

不要把所有上下文都叫“长期记忆”。这个项目里，近期原始消息、历史摘要、知识证据和工具观察来自不同位置，也有不同的生命周期。

机制为什么需要实现要点
近期记忆保留对话措辞与细节默认最近 12 条原始消息；不把所有历史无限发送给模型。
增量摘要压缩越来越长的上下文按 created_at、id、offset 游标顺序消费旧消息；长消息分段推进，成功后原子更新游标。
并发与故障避免重复摘要和互相覆盖会话行锁 + SKIP LOCKED；默认摘要总预算 15 秒；失败只回滚摘要事务。
禁用 / 删除摘要尊重用户对记忆的控制保留已处理的来源边界；后续摘要不重放已遗忘历史，也不继续使用禁用摘要作种子。
上下文预算控制成本、延迟与输入上限默认总输入 48,000 字符；当前请求不静默截断，过长则在图执行前拒绝。记录裁剪诊断。
三个面试边界

① 摘要是有损压缩，可能遗漏信息；② 当前实现是会话内摘要，不是跨会话的用户画像系统；③ 字符预算不是模型 tokenizer 的精确 token 预算，后续可增加模型对应的 token 估算。

CHAPTER 09

后台任务：可靠性来自数据库中的执行身份

前台请求和浏览器连接绑定，后台任务需要独立存活。项目把 Task 记录作为持久化队列，调度器领取工作，Worker 再复用相同的 AgentRuntime。

四个可靠性关键词，逐个解释

01 / LEASE

租约与心跳

领取工作后暂时拥有执行权，心跳续期。租约到期意味着执行身份不再可信；恢复器判断是否还能安全重试。默认心跳 15 秒、租约 180 秒。

02 / FENCING TOKEN

执行代次隔离

每次尝试生成新的 UUID token。旧 Worker 即使恢复运行，也无法用旧 token 提交进度、消息或新工具调用，防止“僵尸 Worker”污染结果。

03 / REPLAY BARRIER

重放屏障

工具派发前或答案持久化时先留下屏障。屏障后的失败或恢复不再自动重试，包括读工具，因为远端“只读”标注不足以证明真正无副作用。

04 / DEADLINE

单次时限与总期限

认证与授权不是同一件事

安全机制当前实现为何这样设计
密码存储Argon2id；旧 PBKDF2 在成功登录时升级密码不能明文保存；哈希在工作线程运行，并限制昂贵操作的并发。
会话机制256 bit 随机 opaque token；只存 SHA-256 hash不是 JWT；可以直接在数据库撤销和约束会话数量。
会话生命周期默认绝对有效期 7 天、API 不活跃 1 天、最多 5 个活跃会话可退出当前 / 所有会话；轮询算 API 活跃，不代表人在键鼠操作。

访问失败处理401 清理过期会话；网络 / 503 保留凭据以便重试区分“已失效的身份”和“临时服务故障”，减少错误登出。

三个容易低估的交互问题

旧流不能写到新对话

AbortController 用于取消；StreamScope 递增版本用于忽略迟到回调。取消与隔离共同处理切换会话和登出时的异步竞态。

确认卡不能一闪而过

待确认轨迹同时考虑实时事件和持久化消息，流状态结束或刷新不会随意抹掉 pending approval。

答案要安全、可阅读

react-markdown + GFM 渲染正文，代码可复制；后端抑制 DSML 等工具协议泄漏；移动端 Runtime 使用抽屉 / 底部面板。

为什么采用 SSE？

主要通信方向是“客户端发一次请求，服务端持续输出状态和文字”，SSE 的事件模型正好适配。若以后需要频繁双向实时控制，可评估 WebSocket；当前取消可以中止请求，确认则是新的 POST。

事件流，不等于当前正文逐 token 显示

当前 _generate_answer 先收集 ModelGateway 的全部文本片段，再整体清洗工具协议，最后通常以一个 token 事件发出正文。运行状态仍实时通过 SSE 更新；前端协议具备增量拼接能力，但不要把当前体验说成严格的逐 token 打字。这样处理优先防止跨片段协议泄漏，代价是首段正文等待更久。

21 · 结合项目说一下 ACID，事务能保证工具只执行一次吗？先练

可以这样回答

原子性是事务内的修改一起提交或回滚；一致性是维护约束和合法状态；隔离性是控制并发事务之间的影响；持久性是已确认提交的数据按数据库配置保存下来。原子性允许失败，不是说操作不能被打断。

拿工具确认为例，检查审批状态和认领授权放在同一个事务里。但授权提交后，外部工具才真正执行，它不属于这个数据库事务。所以数据库事务能保护审批竞争，不能单独保证整个外部操作恰好执行一次。

代码核对 / 继续追问

代码未将整个系统显式设为 SERIALIZABLE；数据库约束也不能替代业务判断。

from heapq import heappush, heapreplace

def top_k(scores, k):
    if k <= 0:
        return []
    heap = []
    for score in scores:
        if len(heap) < k:
            heappush(heap, score)
        elif score > heap[0]:
            heapreplace(heap, score)
    return sorted(heap, reverse=True)
